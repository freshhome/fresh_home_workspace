## 1. الملخص التنفيذي (Executive Summary)

تم إجراء فحص وتتبع دقيق لكود مسار الحجز الفعلي في واجهة الويب [`apps/customer_web/src/app/booking/page.tsx`](file:///d:/fresh_home_workspace/apps/customer_web/src/app/booking/page.tsx)، وملفات المنطق وقاعدة البيانات في [`supabase/migrations`](file:///d:/fresh_home_workspace/supabase/migrations)، ومنظومة التحليلات الحالية في [`src/lib/gtm.ts`](file:///d:/fresh_home_workspace/apps/customer_web/src/lib/gtm.ts).

### أهم نتيجة خرج بها التدقيق (Core Finding):
> **الإجابة الصريحة والمباشرة على السؤال الجوهري:**
> *"هل يمكننا استغلال عمليات Supabase الموجودة بالفعل لتسجيل مراحل الحجز بدل إرسال Tracking Requests منفصلة؟"*
>
> **النتيجة الهندسية من واقع الكود الفعلي:**
> من بين الخطوات الخمس لمسار الحجز، **توجد عمليتان فقط تتصلان بـ Backend/Supabase**، بينما **الخطوات الثلاث الأخرى هي عمليات واجهة أمامية (Pure Frontend State Transitions) لا ترسل أي طلبات إلى Supabase نهائياً**.
>
> 1. **اختيار الخدمة (Step 1):** لا توجد عملية Supabase عند الاختيار؛ شجرة الخدمات تُحمّل بالكامل مرة واحدة في الذاكرة.
> 2. **حساب السعر (Step 2):** ✅ توجد عملية `supabase.rpc("calculate_booking_price")`.
> 3. **اختيار الموعد (Step 3):** ❌ **لا توجد أي عملية Supabase** عند اختيار التاريخ أو الفترة أو الضغط على "التالي".
> 4. **إدخال العنوان (Step 4):** ❌ **لا توجد أي عملية Supabase** عند كتابة العنوان أو المحافظة أو الضغط على "التالي".
> 5. **إنشاء الحجز (Step 5):** ✅ توجد عملية `supabase.rpc("create_atomic_booking")`.
>
> **الاستنتاج الحاسم:**
> الاعتماد **الحصري** على عمليات Supabase الحالية (الحل B بمفرده) **مستحيل تقنياً** لمعرفة أين يخرج المستخدم بين الخطوة 2 و 5، لأن السيرفر ببساطة لن يعلم ما إذا كان العميل خرج عند شاشة المواعيد (Step 3) أم عند شاشة العنوان (Step 4) أم عند شاشة التأكيد؛ فكل هؤلاء سيظهرون للسيرفر كـ "حسب السعر ولم يحجز". 
> بالتالي، لا بد من آلية تتبع واضحة ترصد الخطوات الوسيطة، ويوضح هذا التقرير الخيارات المتاحة والمفاضلة الهندسية بينها.

## 3. خريطة رحلة الحجز الفعلية خطوة بخطوة (Actual Booking Flow Trace)

### المرحلة 1: اختيار الخدمة (Service Selection)
* **أين يختار المستخدم؟**
  * داخل الخطوة `currentStep === 0`، عبر شجرة الخدمات التفاعلية (المبنية بـ Framer Motion).
* **ماذا يحدث عند فتح `/booking`؟**
  * يتم استدعاء استعلام عام لجلب شجرة الخدمات النشطة بالكامل:
    ```typescript
    const { data } = await supabase.from("active_services_tree").select("*").order("sort_order", { ascending: true });
    ```
  * مجرد فتح الصفحة لا يعني إطلاقاً أن المستخدم بدأ الحجز؛ قد يكون زائراً عابراً يتصفح الأقسام الرئيسية.
* **ماذا يحدث عند اختيار خدمة فرعية قابلة للحجز (`isBookableLeaf`)؟**
  * الكود ينفذ تحديثاً محلياً للحالة فقط (السطر 1215):
    ```typescript
    setSelectedSubService(node);
    setSubServiceId(node.id);
    ```
  * **هل يوجد أي Request لـ Supabase عند الاختيار؟** ❌ **لا يوجد أي Request تسجيل أو اتصال إضافي.**
  * في نفس اللحظة، يعمل `useEffect` فرعي (السطر 586) لجلب الأيام المتاحة للخدمة في الخلفية عبر `get_available_days`.

### المرحلة 2: حساب السعر (Price Calculation)
* **الملف والـ Function:**
  * الملف: [`apps/customer_web/src/app/booking/page.tsx`](file:///d:/fresh_home_workspace/apps/customer_web/src/app/booking/page.tsx)
  * الدالة: `handleCalculate()` (السطر 645 إلى 828).
* **طريقة التنفيذ:**
  * استدعاء Supabase RPC مباشرة:
    ```typescript
    const [{ data, error }] = await Promise.all([
      supabase.rpc("calculate_booking_price", {
        p_sub_service_id: subServiceId,
        p_pricing_inputs: inputs
      }),
      new Promise((resolve) => setTimeout(resolve, 750))
    ]);
    ```
* **البيانات المرسلة:**
  * `p_sub_service_id` (نص معرّف الخدمة الفرعية مثل `"FH-S-100009"`).
  * `p_pricing_inputs` (كائن JSONB يحتوي على المساحة، عدد الغرف، الحمامات، التكييفات، قطاعات النوافذ، والخيارات الإضافية).
* **البيانات الراجعة من Supabase:**
  * كائن JSONB: `{ basePrice, extraFees, discount, total, metadata }`.
* **أين يتم التأكد من النجاح؟**
  * السطور 778-792: فحص `if (error) throw error;` ثم قراءة `data.total` وحفظه في State وتفعيل `setHasCalculated(true)`.
* **هل يوجد Session/Booking Identifier موجود حالياً؟**
  * ❌ **لا يوجد أي معرف جلسة يُرسل إلى `calculate_booking_price`**. الدالة في قاعدة البيانات دالة حسابية نقية (Pure Calculation Function) لا تحفظ أي صف ولا تعرف هوية المتصفح.
* **هل يمكن تسجيل وصول المستخدم داخل نفس العملية؟**
  * نظرياً: يمكن تعديل SQL Function لتسجل في جدول أحداث إذا تم تمرير `session_id`.
  * **ولكن هندسياً وتطبيقياً:** دالة `calculate_booking_price` مستدعاة أيضاً من تطبيقات أخرى مثل التطبيق المشترك للعميل والفني [`packages/shared/lib/data/booking/datasources/booking_remote_datasource.dart`](file:///d:/fresh_home_workspace/packages/shared/lib/data/booking/datasources/booking_remote_datasource.dart) ومحاكي التسعير في لوحة الإدارة. إقحام كتابة إحصائيات داخل دالة تسعير عامة يخل بمبدأ المسؤولية الواحدة (Single Responsibility Principle) ويؤدي لتسجيل أحداث وهمية عند كل تجربة تسعير في لوحة الإدارة.

### المرحلة 3: اختيار الموعد (Schedule Selection)
* **كيف يتم جلب المواعيد المتاحة؟**
  * عبر استدعاء `supabase.rpc("get_available_days", { p_sub_service_id, p_start_date, p_end_date })` في السطر 597.

  * بالتالي: **جلب المواعيد لا يعني إطلاقاً أن العميل وصل إلى خطوة الموعد أو اختار موعداً.**
* **أين يتم اختيار الموعد والتحقق من صلاحيته؟**
  * المستخدم يختار يدوياً يوماً وفترة زمنية (`scheduledDate`, `scheduledTime`).
  * التحقق يتم محلياً في دالة `isStepValid()` (السطر 926):

    case 1:
      return scheduledDate !== "" && scheduledTime !== "" && availabilityMap[scheduledDate] !== false;

* **ماذا يحدث عند الضغط على "التالي" (`handleNext`)؟**

    } else if (currentStep === 1) {

  * **النتيجة الفورية:** ❌ **لا توجد أي عملية Backend أو Supabase نهائياً عند تجاوز خطوة الموعد.** يتم فقط تغيير الـ State والانتقال لشاشة العنوان.

### المرحلة 5: التأكيد وإنشاء الحجز النهائي (Booking Creation)
* **الدالة المسؤولة:**
  * `handleCompleteBooking()` في السطور 1071-1209.
* **العملية الفعلية مع Supabase:**
  * استدعاء الدالة الذرية: `supabase.rpc("create_atomic_booking", { ... })`.
* **ماذا تفعل `create_atomic_booking` في قاعدة البيانات؟**
  * مبنية ومحصنة في ملف الهجرة [`107_authoritative_guest_booking_flow.sql`](file:///d:/fresh_home_workspace/supabase/migrations/107_authoritative_guest_booking_flow.sql):
    1. تتحقق من الصلاحيات وكون العميل Guest أو مسجل.
    2. تفحص النطاق الجغرافي الصارم (القاهرة والجيزة فقط).
    3. تعيد حساب السعر إلزامياً على السيرفر عبر `execute_pricing_pipeline` لمنع أي تلاعب في أسعار الواجهة.
    4. تفحص الحجوزات المكررة للضيوف لمنع السبام.
    5. **فحص الطاقة الاستيعابية وتوفر الفني (Capacity & Technician Check):**
       * تستدعي `public.get_available_technicians(p_sub_service_id, p_scheduled_day)`.
       * إذا لم يتوفر فني متاح، **ترفض العملية فوراً وتلقي استثناء:**
         ```sql
         RAISE EXCEPTION 'لا يوجد فني متاح لهذا اليوم' USING ERRCODE = 'P0002';
         ```
       * **لا يوجد أي تخصيص وهمي لفني إذا لم تكن هناك طاقة استيعابية.**
    6. في حال توفر الفني، تضع قفل تزامن (`pg_advisory_xact_lock`) لمنع التضارب، ثم تنشئ الحجز في جدول `public.bookings`.
    7. تُرجع المعرف النهائي للحجز `v_booking_id` (UUID).
* **متى نعرف أن الحجز نجح فعلياً؟**
  * فقط عند عودة `bookingId` بدون `bookingError`.
  * عندئذٍ فقط، يتم التوجيه إلى `/orders?bookingId=...&success=true`، وحفظ علامة النجاح في الذاكرة، ثم تسجيل `trackPurchase` الفعلي.
  * **الضغط على زر "تأكيد الحجز" وحده لا يعني إتمام الحجز أبداً؛ فلو فشلت الطاقة الاستيعابية أو تعطل الاتصال، يتم إظهار Alert للعميل ولا يتم احتساب حجز.**

## 5. العمليات التي يمكن / لا يمكن استغلالها للـ Tracking

### ما يمكن استغلاله مباشرة:
1. **الخطوة 5 (تأكيد الحجز النهائي):**
   * عملية `create_atomic_booking` هي المصدر الحقيقي الموثوق الوحيد (**Single Source of Truth**) لنجاح الحجز.
   * يمكن استغلال نجاحها إما بتسجيل حدث الإتمام أو تمرير معرف الجلسة `session_id` ضمن `p_pricing_inputs` ليرتبط بجدول الحجوزات.

### ما لا يمكن استغلاله (الحقيقة المعمارية):
1. **الخطوة 1 (بدء الحجز الحقيقي):**
   * لا يوجد طلب شبكة عند اختيار الخدمة؛ فالشجرة كاملة في الذاكرة. لا يمكن رصد هذه الخطوة إلا بحدث يتم إطلاقه من الـ Frontend عند اختيار العميل للخدمة الفرعية.
2. **الخطوة 3 (اختيار الموعد):**
   * لا يوجد أي طلب للـ Backend عند اختيار الموعد أو عند الضغط على زر "التالي" للانتقال للعنوان. محاولة استغلال `get_available_days` ستعطي أرقاماً مضللة لأنها تعمل قبل أن يصل المستخدم للموعد.
3. **الخطوة 4 (إدخال العنوان):**
   * لا يوجد أي اتصال بقاعدة البيانات عند تعبئة العنوان أو الضغط على "التالي". العناوين لا تُرسل إلى السيرفر إلا في اللحظة الأخيرة عند إنشاء الحجز.

## 6. تقييم ومقارنة الحلول الهندسية

### الحل A: إرسال أحداث تتبع منفصلة إلى Supabase (Dedicated Tracking Requests)
* **الفكرة:** إنشاء جدول خفيف `booking_funnel_events` وإرسال حدث مستقل من واجهة الويب (`customer_web`) عند إنجاز كل خطوة حقيقية (عبر `fetch` بخاصية `keepalive` لضمان عدم التعطيل).
* **المميزات:**
  * يحل بدقة رصد الخطوات التي ليس لها Backend (الخطوة 1، 3، 4).
  * بيانات فورية (Real-time 100%) تظهر في تطبيق المدير بلحظتها دون أي تأخير.
  * لا يلمس أو يغير أي منطق في دوال التسعير والحجز (`calculate_booking_price` / `create_atomic_booking`).
  * يعمل بكفاءة تامة مع الـ Guests والمسجلين.
* **العيوب / Trade-offs:**
  * يضيف طلبات شبكة إضافية خفيفة (بين 2 إلى 4 طلبات لكل مستخدم يكمل المسار كاملاً).

---

### الحل B: حشر التتبع داخل عمليات Supabase الحالية (Piggybacking on Existing RPCs)
* **الفكرة:** تعديل `calculate_booking_price` لتسجل الخطوة 2، وتعديل `create_atomic_booking` لتسجل الخطوة 5.
* **التقييم الحاسم:**
  * **عجز وظيفي كامل (Functional Impossibility):** لن تستطيع رصد الخطوة 1 (اختيار الخدمة)، ولا الخطوة 3 (الموعد)، ولا الخطوة 4 (العنوان) لأنه لا توجد عمليات Backend لتلك الخطوات!
  * **تضارب في الـ Business Logic:** دالة `calculate_booking_price` تستخدمها تطبيقات الجوال الخاصة بالعملاء والفنيين ومحاكي الأسعار، وتعديلها لتسجيل جلسات ويب سيؤدي إلى بيانات مشوهة وتلوث في المعمارية (Coupling).
  * **النتيجة:** حل غير قابل للتطبيق بمفرده ولا يحقق الهدف المطلوب بمعرفة "أين خرج العميل بالضبط".

---

### الحل C: الاعتماد الحصري على Google Analytics و GTM
* **الفكرة:** الاستفادة من أحداث `dataLayer` الموجودة بالفعل حالياً في `customer_web` (`calculate_price`, `checkout_progress`, `purchase`).
* **المميزات:**
  * الكود موجود بالفعل في الموقع ولا يحتاج أي تعديل في الـ Frontend!
  * صفر طلبات إضافية على Supabase.
* **العيوب / Trade-offs:**
  * **التأخير الزمني (Latency):** بيانات Google Analytics Data API تأخذ من 24 إلى 48 ساعة لتظهر في تقارير الأبعاد المخصصة (Custom Dimensions)، مما يجعل متابعة مديري المنصة للتحليلات اللحظية غير ممكنة عبر API بسيط.
  * **صعوبة الفلترة الفورية:** ربط الأحداث المخصصة بفلاتر الخدمات في تطبيق المدير Flutter يتطلب بناء بنية معقدة عبر Google Analytics Reporting API مع حدود استهلاك صارمة (Quotas).
  * **حجب التتبع:** موانع الإعلانات (Ad-blockers) تحجب Google Tag Manager لدى نسبة من الزوار.

---

### الحل D (الموصى به هندسياً): الحل الهجين الذكي (Smart Hybrid Event Pipeline)
* **الفكرة:**
  1. **الحفاظ على Google Analytics / GTM:** للإحصائيات التسويقية، مصادر الحملات الإعلانية (UTM Parameters)، ومسارات التحويل بعيدة المدى.
  2. **إنشاء جدول أحداث مسار الحجز اللحظي في Supabase:** يستقبل إشارات الانتقال المؤكدة فقط:
     * **Step 1:** عند اختيار خدمة فرعية صالحة.
     * **Step 2:** عند نجاح حساب السعر الفعلي.
     * **Step 3:** عند تجاوز خطوة الموعد بموعد صالح فعلياً.
     * **Step 4:** عند تجاوز خطوة العنوان بعنوان مدعوم ومستوفٍ.
     * **Step 5:** عند نجاح `create_atomic_booking` وعودة المعرف.
  3. **استخدام دمج ذكي في الخطوة 5:** يمكن تمرير `session_id` مع كائن `p_pricing_inputs` في `create_atomic_booking` لربط جلسة الحجز بالسجل الحقيقي مباشرة، مما يربط التحليلات بقاعدة البيانات بأعلى دقة ممكنة.

## 7. جدول المقارنة الشاملة للحلول (Comparative Trade-offs Matrix)

| المعيار الهندسي | الحل A: طلبات منفصلة في Supabase | الحل B: حشر التتبع في العمليات الحالية | الحل C: الاعتماد على Google Analytics فقط | الحل D: الهجين الذكي (الموصى به) |
| :--- | :--- | :--- | :--- | :--- |
| **الدقة في معرفة موضع خروج العميل** | عالية جداً (Real-time) | **فاشلة (لا ترصد خطوات 1 و 3 و 4)** | جيدة لكن متأخرة 24-48 ساعة | **فائقة وتجمع اللحظية مع الأبعاد التسويقية** |
| **عدد طلبات Supabase الإضافية** | 2 - 4 طلبات خفيفة لكل رحلة حجز | صفر طلبات إضافية | صفر طلبات | 2 - 4 طلبات خفيفة جداً (Fire & Forget) |
| **التأثير على سرعة الموقع (UX Performance)** | معدوم (`fetch` مع `keepalive` غير معطل) | معدوم | معدوم | **معدوم كلياً** |
| **التأثير على Business Logic الداخلي** | معدوم (معزول تماماً) | **سلبي وخطير (تعديل دوال التسعير العامة)** | معدوم | **معدوم (لا يمس منطق التسعير أو الحجز)** |
| **التعامل مع العميل الزائر (Guest)** | ممتاز (عبر `session_id` و `browser_id`) | محصور في عمليتين فقط | ممتاز | **ممتاز ومتوافق مع بنية الـ Guest الحالية** |
| **التعامل مع التكرار و Refresh و Back** | محمي بقيد فريد `(session_id, step)` | غير محمي في الخطوات الوسيطة | يحتاج إعدادات De-duplication معقدة | **محمي بقيد فريد و Distinct Count** |
| **ربط المصدر الإعلاني (UTM / Campaigns)** | يحتاج تخزين حقول إضافية | لا يدعم | ممتاز وأصيل في GA4 | **الأفضل (GA4 للمصدر و Supabase للمسار اللحظي)** |
| **الظهور اللحظي في تطبيق المدير (Flutter)** | لحظي في نفس الثانية | لحظي لكنه ناقص بنسبة 60% | متأخر (يوم أو يومين) | **لحظي ومباشر عبر RPC سريع جداً** |

## 8. التوصية الهندسية النهائية (Final Engineering Recommendation)

بناءً على فحص الأكواد والعمليات الفعلية، نوصي باعتماد **الحل D (الهجين الذكي)** للأسباب الهندسية التالية:

1. **احترام الواقع البرمجي:** لا توجد عمليات في Backend لخطوات المواعيد والعنوان؛ لذا فإن تسجيلها عبر واجهة الويب هو السبيل التقني الوحيد لتمكين مديري المنصة من معرفة هل العميل هرب بسبب السعر، أم بسبب المواعيد، أم بسبب العنوان.
2. **حماية المنطق الأساسي للمنصة (Core Domain Protection):** دالة `calculate_booking_price` ودالة `create_atomic_booking` من أهم الدوال الحساسة مالياً وتشغيلياً في النظام. إقحام كود تسجيل إحصائيات بداخلها سيخلق ارتباطاً غير صحي (Tight Coupling) ويعرض عمليات التطبيقات الأخرى للتأثر.
3. **أداء لا تشوبه شائبة للعميل:** تسجيل الخطوات في جدول `booking_funnel_events` عبر استدعاءات `fetch` في الخلفية بخاصية `keepalive` لا ينتظرها العميل، ولا تظهر أي علامة تحميل، وإذا فشلت أو انقطعت الشبكة لا تؤثر أبداً على استمرار العميل في حجزه.
4. **تكامل متناسق مع تطبيق المدير:** يتيح بناء واجهة تفاعلية لحظية (Real-Time Visual Funnel) في تطبيق المدير تعرض نسب التسرب الدقيقة لكل مرحلة.

## 9. نقاط وقرارات استراتيجية مطروحة للنقاش (Decisions for Review)

قبل الانتقال لأي مرحلة تنفيذية، هذه النقاط تتطلب موافقتك وتفضيلك:

1. **هل ترغب في اعتماد الحل D (الهجين الذكي)؟**  
   حيث نحتفظ بـ Google Analytics للتقارير التسويقية، وننشئ جدولاً خفيفاً في Supabase لرصد المسار اللحظي والانسحاب بدقة دون لمس كود الـ Business Logic في دوال التسعير.
2. **هل نعتمد ربط `session_id` داخل `create_atomic_booking`؟**  
   بحيث يتم إرسال `session_id` كحقل اختياري إحصائي داخل كائن `pricing_inputs` الحالي دون الحاجة لتغيير معاملات الدالة الأساسية.
