## 1. الهدف ونطاق العمل (Objective & Scope)

تهدف هذه الوثيقة إلى تحديد القواعد التشغيلية والتقنية الصارمة والنهائية لنظام **حجز الزوار غير المسجلين (Guest Booking)** في منصة Fresh Home.

تمثل هذه القواعد المرجع الأساسي المعتمد لسلوك النظام عبر كامل المكونات:
* الواجهة الأمامية للعميل (`apps/customer_web`).
* واجهات وقواعد بيانات Supabase Backend (`PostgreSQL RPCs`, `RLS Policies`, `Triggers`, `Cron Jobs`).
* لوحة تحكم وتطبيق الإدارة (`apps/fresh_home_admin`).
* تطبيق الفنيين والأسطول الميداني (`apps/technician_app`).

## 2. القواعد الأساسية لحجز الزوار (The Two Core Rules)

ينقسم تعامل النظام مع حجز الزائر (Guest Booking) إلى **حالتين اثنتين فقط لا غير**:

```
                              [ طلب حجز من زائر Guest ]
                                         │
                                         ▼
            ┌───────────────────────────────────────────────────────────┐
            │  هل يوجد حجز سابق لنفس الزائر في نفس اليوم ونفس نوع الخدمة؟  │
            └───────────────────────────────────────────────────────────┘
                                         │
                        ┌────────────────┴────────────────┐
                        ▼                                 ▼
                     [ لا ]                             [ نعم ]
                        │                                 │
                        ▼                                 ▼
            ┌───────────────────────┐         ┌───────────────────────┐
            │   الحالة الأولى (Case 1)   │         │   الحالة الثانية (Case 2)  │
            │   أول حجز للـ Guest    │         │  تكرار نفس اليوم والخدمة │
            │                       │         │                       │
            │ • حجز طبيعي ومؤكد فوراً │         │ • يتطلب تأكيد واتساب   │
            │ • حجز سعة وتعيين فني   │         │ • لا استهلاك للسعة    │
            │ • تجربة انسيابية وسلسة │         │ • لا تعيين فني مسبق   │
            └───────────────────────┘         └───────────────────────┘
```

---

### الحالة الأولى: أول حجز للـ Guest (First Guest Booking)

إذا كان العميل الزائر يُجري أول حجز له (أو ليس لديه حجز نشط سابق لنفس اليوم ونفس نوع الخدمة):

1. **تجربة حجز انسيابية بالكامل (Frictionless Experience):**
   * بدون تسجيل دخول إجباري (No Mandatory Login).
   * بدون كود تحقق بالرسائل (No OTP).
   * بدون اختبارات تحقق أمنية مزعجة (No CAPTCHA / Cloudflare Turnstile).
   * بدون اشتراط تأكيد عبر واتساب (No WhatsApp Confirmation Required).
2. **سلوك النظام وقاعدة البيانات:**
   * يتم إنشاء الحجز وتأكيده مباشرة (`is_whatsapp_confirmed = true`).
   * يتم فحص السعة الاستيعابية المتاحة وتخصيص فني معتمد فوراً من الأسطول (`status = 'assigned'`).
   * يتم حجز الطاقة الاستيعابية اليومية للخدمة والفني بشكل رسمي (`Capacity Reserved`).
   * يدخل الحجز في المسار التشغيلي الطبيعي (تصل إشعارات التكليف للفني ويظهر في جدول أعماله).
3. **الهدف البيزنسي:**
   * تحقيق أعلى معدل تحويل للطلبات (Conversion Rate) وإزالة أي عوائق أمام العميل الحقيقي الذي يطلب الخدمة لأول مرة.

---

### الحالة الثانية: Guest لديه حجز بالفعل لنفس اليوم ونفس نوع الخدمة (Duplicate Same-Day, Same-Service)

إذا حاول نفس العميل الزائر إنشاء حجز آخر، وكان لديه بالفعل حجز سابق نشط (غير ملغي):
1. **لنفس اليوم المجدول (`scheduled_day`).**
2. **ولنفس نوع الخدمة (`service_id` أو نفس فئة الخدمة الرئيسية).**

فإن الحجز الحالي **لا يتم قبوله كحجز مؤكد فوري**، بل يتطلب **تأكيداً عبر الواتساب (Requires WhatsApp Confirmation)**.

#### تجربة العميل والنبرة التواصلية (Customer UX & Tone):
* **الاحترام والمهنية المطلقة:**
  * العميل لا يُرفض طلبه ولا يُحظر.
  * لا تظهر للعميل أي رسالة تنعته بأنه مشبوه، أو احتيالي، أو سبام (No "Spam", "Fraud", or "Suspicious" labels).
* **الرسالة الموجهة للعميل:**
  تظهر له رسالة توضيحية محترمة وهادئة في الواجهة:
  > *"لديك حجز بالفعل لهذه الخدمة في نفس اليوم. لتأكيد الحجز الحالي، يرجى التأكيد عبر WhatsApp."*
* **آلية المتابعة:**
  * يظهر للعميل زر مباشر للانتقال إلى محادثة الدعم عبر الواتساب (`wa.me`) لتأكيد الحجز، مع عرض مؤقت زمني لانتظار التأكيد (مهلة 60 دقيقة محددة من النظام).

## 3. معايير تحديد "نفس الـ Guest" (Defining "Same Guest" Identity Signals)

نظراً لأن العميل الزائر غير مسجل الدخول (`auth.uid() IS NULL`)، لا توجد هوية قطعية موثقة ببيانات اعتماد للمستخدم (No Authenticated Identity).  
لذلك يتم التعامل مع كافة المعرّفات المتاحة كـ **إشارات مساعدة (Signals)** تُمكن الـ Backend من الربط بين الحجوزات، دون اعتبار أي منها هوية مؤكدة للمستخدم:

### 1. الإشارات المتاحة للربط (Available Correlation Signals)
1. **رقم هاتف الاتصال (`contact_phone`):**
   * إشارة مساعدة يُدخلها العميل في خطوة بيانات التواصل (يتم توحيد صيغتها برمجياً لتسهيل المقارنة).
   * رقم الهاتف وحده ليس هوية قطعية للمستخدم، ولا يعتبر شرطاً منفرداً أو مفتاحاً رئيسياً إلزامياً (Not a Primary Key Signal).
2. **معرّف المتصفح / الجهاز (`browser_id`):**
   * إشارة مساعدة مهمة للربط؛ معرّف عشوائي يُنشأ في المتصفح ويُخزن محلياً لتتبع الجلسة وتمريره مع طلب الحجز.
   * ليس هوية مطلقة للمستخدم؛ ولا يُعتبر وجوده أو تطابقه شرطاً منفرداً إلزامياً إذا كان ذلك سيؤدي إلى نتائج إيجابية خاطئة (False Positives).
3. **عنوان الـ IP و الـ User-Agent:**
   * إشارات مساعدة إضافية تُلتقط على مستوى طلب الـ Backend.
   * لا يُستخدم عنوان الـ IP وحده أبداً لتحديد هوية العميل الزائر نظراً لاحتمالية مشاركة عدة مستخدمين لنفس الـ Public IP (مثل شبكات المحمول والـ CGNAT في مصر).

### 2. معيار الربط المعتمد في الـ Backend (Authoritative Correlation Criterion)
* **القاعدة التشغيلية الحاكمة:**
  > **يحدد الـ Backend في مرحلة Development Planning آلية المطابقة التقنية الدقيقة بين حجوزات الـ Guest، بعد فحص الـ schema والـ existing implementation، مع الالتزام بالإشارات المتاحة وعدم إضافة أي Risk Score أو نظام Anti-Fraud معقد.**
* **ضوابط ومحددات الربط:**
  * جميع المعرّفات المتاحة (`phone`, `browser_id`, `IP`, `User-Agent`) هي إشارات تعاونية تساعد الـ Backend في الربط المنطقي والموثوق.
  * لا يتم بناء أي درجات مخاطرة (No Risk Score) ولا مستويات تقييم (Low / Medium / High) ولا منظومة تحليل سلوكي أو مكافحة احتيال معقدة.
  * ينصب تركيز الـ Backend حصرياً على التحقق الموثوق من أن الحجزين لنفس الزائر في نفس اليوم لنفس الخدمة، بما يحافظ على سلاسة الحجز ويمنع تعطيل أو إزعاج العملاء الحقيقيين.

## 4. حدود النطاق وتجنب التعقيد غير المطلوب (Anti-Spam Scope Boundaries)

**تأكيد حاسم:** النظام الحالي **ليس** مطلوباً منه بناء منظومة مكافحة احتيال شاملة (Full Anti-Fraud Engine).

المحددات المستبعدة صراحةً من هذه المرحلة:
* ❌ لا يوجد تقييم مخاطر متعدد المستويات (No Multi-level Risk Scoring: Low / Medium / High).
* ❌ لا يوجد تحليل سلوكي معقد لحركات الفأرة أو سرعة ملء الحقول (No Behavioral Analysis).
* ❌ لا توجد مراقبة وملاحقة للحجوزات على مدار أسابيع أو شهور سابقة (No Cross-Week Tracking).
* ❌ لا يتم منع أو تقييد العميل بناءً على إجمالي عدد حجوزاته السابقة في المنصة بشكل عام.
* ❌ لا يوجد OTP للزوار عبر الرسائل القصيرة.
* ❌ لا يوجد تسجيل دخول إجباري (No Forced Login).
* ❌ لا يوجد CAPTCHA من أي نوع.

**النطاق الحصري المعتمد:**
> **"نفس الـ Guest + لديه حجز سابق غير ملغي + لنفس اليوم + لنفس نوع الخدمة → الحجز الحالي يتطلب تأكيد WhatsApp."**

## 5. السيناريو المؤجل مستقبلاً (Deferred Scenario — Future Enhancement)

### السيناريو:
محاولة منافس أو جهة مسيئة إغراق النظام بحجوزات متفرقة يومياً ولكن عبر أيام مختلفة متتالية:
* Booking 1 ➔ Day 1 ➔ Service A
* Booking 2 ➔ Day 2 ➔ Service A
* Booking 3 ➔ Day 3 ➔ Service A
* وهكذا...

### الوضع المعتمد للتعامل مع هذا السيناريو:
* **مؤجل تماماً (Deferred / Future Anti-Spam Enhancement).**
* لن تتم معالجته في هذه المرحلة تجنباً لتعقيد النظام أو إعاقة العملاء الحقيقيين الذين قد يحجزون خدمات دورية لأيام قادمة.
* سيتم التعامل معه لاحقاً كمنظومة منفصلة خاصة بلوحة الإدارة (Admin Monitoring / Heuristics) لمراقبة الأنماط غير الطبيعية.

## 6. قواعد الطاقة الاستيعابية والأسطول (Technician Capacity & Allocation Rules)

هذه القاعدة تعالج العيب الجذري الموجود في النظام القديم:

### السلوك الإلزامي للحجز الذي يتطلب تأكيد واتساب:
1. **لا يعتبر حجزاً مؤكداً (Not Confirmed):** لا يكتسب صفة الحجز المعتمد.
2. **عدم حجز الطاقة الاستيعابية نهائياً (Zero Capacity Consumption):**
   * لا يتم خصم أي نقطة طاقة من السعة اليومية للفنيين (`max_daily_capacity`).
   * لا يظهر كحمل مسند أو غير مسند في دالة حساب السعة `get_available_technicians`.
   * تظل سعة اليوم متاحة بالكامل للعملاء الحقيقيين الآخرين.
3. **عدم تخصيص فني مسبقاً (No Technician Pre-assignment):**
   * يظل حقل الفني فارغاً (`technician_id = NULL`) طالما الحجز معلقاً بانتظار الواتساب.
   * لا يتم قفل الفني بـ `advisory lock` أو إسناده لحجز لم يتأكد بعد.
4. **حجب الحجز عن الفنيين وتطبيقاتهم (Zero Technician Visibility):**
   * الفني لا يرى الحجز إطلاقاً في تطبيقه الميداني.
   * لا يُرسل أي إشعار (Push Notification / FCM / SMS) للفني.
5. **التأكيد المشروط بالسعة (Capacity-Guaranteed Confirmation):**
   * عندما يقوم العميل بتأكيد الحجز عبر الواتساب (أو يقوم الآدمن بتأكيده يدوياً):
     * يفحص النظام السعة المتاحة في تلك اللحظة.
     * إذا كانت السعة لا تزال متوفرة، يتم تخصيص الفني، حجز الطاقة الاستيعابية، ونقل الحجز فوراً إلى `assigned` وإرسال الإشعارات.
     * إذا نفدت السعة خلال فترة الانتظار، يتم إخطار الإدارة والعميل فوراً لاختيار موعد بديل.

## 7. سلطة ومرجعية الـ Backend الحتمية (Authoritative Backend Enforcement)

* **المرجعية المطلقة لقاعدة البيانات والـ Backend:**
  * قرار ما إذا كان الحجز حراً ومؤكداً فوراً أم يحتاج إلى تأكيد واتساب هو **مسؤولية حصرية لقاعدة البيانات (PostgreSQL Functions / RPC)**.
* **منع التجاوز من الـ Frontend (No Client-side Bypass):**
  * لا يجوز الوثوق بما يرسله المتصفح في أي معامل مثل `p_is_whatsapp_confirmed`.
  * إذا كان الطلب قادماً من زائر (`auth.uid() IS NULL` أو `p_user_id IS NULL`):
    * يتجاهل الـ Backend أي قيمة قادمة من العميل لـ `p_is_whatsapp_confirmed`.
    * تقوم الدالة المركزية `create_atomic_booking` بفحص قاعدة البيانات داخلياً وتطبيق معادلة التكرار.
* **حماية الأمان ضد استدعاءات الـ PostgREST المباشرة:**
  * أي استدعاء خارجي للـ API عبر `cURL` أو `Postman` أو سكربتات لا يمكنه تجاوز قاعدة الواتساب لأن المنطق مفروض على مستوى الـ SQL داخل المعاملة الذرية (Atomic Transaction).

## 8. مصفوفة الحالات والنتائج (Decision Matrix Summary)

| رقم الحالة | طبيعة المستخدم | الحجوزات السابقة لنفس اليوم والخدمة | حالة `is_whatsapp_confirmed` | حالة الحجز في DB | تخصيص فني؟ | استهلاك السعة؟ | ظهور للفني؟ | تجربة العميل |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **1** | عميل مسجل (Auth) | لا ينطبق (مسجل بحساب) | `true` | `assigned` | ✅ نعم | ✅ نعم | ✅ نعم | تأكيد فوري وتتبع مباشر |
| **2** | زائر (Guest) | **لا يوجد** (أول حجز) | `true` | `assigned` | ✅ نعم | ✅ نعم | ✅ نعم | تأكيد فوري وتتبع مباشر |
| **3** | زائر (Guest) | **يوجد حجز نشط** (نفس اليوم + نفس الخدمة) | **`false`** | **`created`** | ❌ **لا (`NULL`)** | ❌ **لا (صفر)** | ❌ **لا (محجوب)** | رسالة مهذبة + طلب تأكيد واتساب + عداد 60 دقيقة |
| **4** | زائر (Guest) | يوجد حجز نشط (**يوم مختلف** + نفس الخدمة) | `true` | `assigned` | ✅ نعم | ✅ نعم | ✅ نعم | تأكيد فوري وتتبع مباشر |
| **5** | زائر (Guest) | يوجد حجز نشط (نفس اليوم + **خدمة مختلفة**) | `true` | `assigned` | ✅ نعم | ✅ نعم | ✅ نعم | تأكيد فوري وتتبع مباشر |
